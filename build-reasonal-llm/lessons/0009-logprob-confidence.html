第 9 课 · 给答案打分：从规则分数到 log-prob 置信度

📖 BRM §5.3–5.6 ⏱ 35–45 分钟 🎯 收获：logprob 打分——它还会在 GRPO 训练目标里再登场

为什么学这个：投票需要并列裁决，self-refinement 需要判断"改完是不是更好"——都需要给答案打分。而且这课的 log-prob 概念是全书最"保值"的知识之一：下一章 RL 训练目标的核心就是它。工作上，你 API 返回的 logprobs 字段从此可解释、可利用。

01打分器 ≠ 验证器

先分清两个东西BRM §5.3：

验证器（ch3）打分器（本课）
前提已知标准答案不知道正确答案
用途评估集上算准确率给候选答案排序/裁决

三种打分器路线BRM §5.3：启发式规则（本课）→ 模型自身概率（本课）→ LLM-as-a-judge（附录 F.5）。

02路线一：启发式分数

两个正确答案（都算出 83），一个 534 tokens、一个 231 tokens——谁更好？书里的规则打分BRM §5.3, listing 5.3：

def heuristic_score(answer, prompt=None, brevity_bonus=500.0, ...):
    score = 0.0
    cand = extract_final_candidate(answer, fallback="none")
    if cand:
        score += 2.0        # boxed_bonus：干净的可抽取答案
    else:
        cand = extract_final_candidate(answer, fallback="number_only")
        if cand:
            score += 1.0    # extract_bonus：至少有个数字
    score += 1.5 * math.exp(-len(answer) / brevity_bonus)  # 简短奖励，指数衰减
    return score
  • 抽取奖励：有 \boxed{} 得 2.0 > 只有裸数字得 1.0 > 长文本 0 分——鼓励"能提取最终答案"的格式。
  • 简短奖励：随长度指数衰减，短答案最多 +1.5，超过 1000 字符只加 0.2 以下——只做 tie-break，不喧宾夺主。

实测：长答案 2.088，短答案 2.517——选短的BRM §5.3。参数值不神圣，相对比例才重要；怎么调看副作用（总偏好无法解析的 → 加抽取分；偏好啰嗦的 → 加简短压力）。

工作联想这个 heuristic_score 就是 ch7 将要实现的 format reward 的雏形——格式奖励进 GRPO，同款思想：奖励"答案好抽取、别啰嗦"。

03路线二：模型自己有多自信？

关键转向：不生成，只审读分数。把 prompt+答案整体喂给模型，在每个位置查"模型给『实际下一个 token』分配的概率"BRM §5.4：

@torch.inference_mode()
def calc_next_token_probas(model, tokenizer, prompt, device):
    token_ids = torch.tensor(tokenizer.encode(prompt), device=device)
    logits = model(token_ids.unsqueeze(0)).squeeze(0)      # [seq_len, vocab]
    all_probas = torch.softmax(logits, dim=-1)
    t_idx = torch.arange(0, token_ids.shape[0] - 1)        # 每个位置
    next_ids = token_ids[1:]                                # 真实下一 token（错位一格）
    next_token_probas = all_probas[t_idx, next_ids]         # 查表
    joint = torch.prod(next_token_probas)                   # 联合概率 = 连乘
    return next_token_probas, joint

书例（"The capital of Germany is __"）BRM §5.4：

序列最后 token 概率联合概率（连乘）
… is Berlin0.1695.9e-08
… is Bridge2.9e-071.0e-13

问题立刻暴露：联合概率是一堆小于 1 的数连乘，越长越接近 0——长序列直接数值下溢（underflow）。

04Log 变换：连乘变连加

解法是统计学习的看家本领BRM §5.5：

联合概率p₁ · p₂ · ⋯ · p_T
—log→
联合 logproblog p₁ + log p₂ + ⋯ + log p_T
图 1 · log 把乘法变加法：既避免下溢，又保序（likelihood 大 ⇔ log-likelihood 大，只是更不"负"）。

上例换算：Berlin −16.63 vs Bridge −29.88——差距清晰可读。代码只改两处：`softmax`→`log_softmax`，`prod`→`sum`BRM §5.5, listing 5.7。logprob 越接近 0 越自信（0 = 概率 1）。

做成打分器还要两步修正BRM §5.6, listing 5.8：① 只算答案 token，排除 prompt（prompt 是你自己写的，不该计入模型的自信）；② 取平均不取总和——否则长答案天然吃亏。

@torch.inference_mode()
def avg_logprob_answer(model, tokenizer, prompt, answer, device="cpu"):
    prompt_ids = tokenizer.encode(prompt)
    answer_ids = tokenizer.encode(answer)
    full_ids = torch.tensor(prompt_ids + answer_ids, device=device)
    logits = model(full_ids.unsqueeze(0)).squeeze(0)
    logprobs = torch.log_softmax(logits, dim=-1)
    start = len(prompt_ids) - 1                          # 只取答案段
    end = full_ids.shape[0] - 1
    t_idx = torch.arange(start, end, device=device)
    next_tokens = full_ids[start + 1 : end + 1]
    return torch.mean(logprobs[t_idx, next_tokens])      # 长度归一化：平均

书例：Berlin 答案 −0.204 vs Bridge 答案 −3.891BRM §5.6。

⚠ 置信 ≠ 正确logprob 度量的是"模型自己多偏好这个答案"，不是"答案多正确"。模型会自信地犯错——流畅、常见、格式漂亮的错误答案可能拿高分（下一课实测：avg logprob 打分器整体表现最差）。它是"若干有用信号之一"，不是万能裁决器。BRM §5.4/5.6
埋个伏笔logprob 在 ch6 强势回归：RLVR/GRPO 的策略梯度就是在"提升高奖励回答的 log-prob、压低低奖励回答的 log-prob"。这课是地基。BRM §5.6

05检索练习

一句话带走 打分 = 在不知答案时排序候选：启发式看格式与长度，logprob 看模型自身置信（答案段平均 log-softmax）。log 化乘为加、避免下溢；但置信不等于正确。
