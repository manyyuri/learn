第 9 课 · flue 架构深潜 · 阶段② 持久与执行

durability：接受的提交，必然走到一个终态

读完这一课，你能讲清 stylist 那行 durability = { maxAttempts: 3, timeoutMs: 300_000 } 到底在买什么——以及「at-least-once 执行、exactly-once 记录」这句总纲怎么落到每一层。

§0开场检索

§1受理契约：submission 的承诺

每条到达 agent 的输入（HTTP prompt、dispatch、init().dispatch、channel、schedule）都作为 submission 受理：payload 在任何模型工作开始前就落盘。202 响应 / dispatch 回执就是这份受理记录。它带着一个承诺：

每个被受理的提交，无论中间崩多少次，都恰好到达一个持久终态——completed / failed / aborted。

终态作为 submission_settled 记录写进会话流——等它的人（SDK 的 wait()、init().read）从那条记录 resolve/reject，跨自身重连也能看到。

  • 每会话一个持久队列：按受理顺序处理，同一时刻一个 submission 在跑；忙时到达的消息在 turn 边界加入当前响应或排队等；排队消息永不丢。
  • attempt 机制：coordinator 认领 → 跑 → settle。一次中断消耗一个 attempt，恢复认领新的，直到花光重试预算。
  • abort 同纪律：POST /:id/abort 对每个未 settle 的提交记录持久中断意图，各自经正常 attempt 机制 settle 成 aborted——即使跑的进程已死。已完成的活不受影响。
guide/durability.md（Submissions and the accepted-work contract）

§2恢复两阶段：先收敛，再分类

崩溃不留自身记录（死进程停笔）。恢复由接替 owner 醒来时触发，只看持久证据。两阶段：

  1. 收敛流（converge）：把死 attempt 留下的半截流式输出无条件、幂等地闭合为 aborted 条目——任何崩溃形状都不会让会话看起来"流到一半"。半截输出保留在历史里。
  2. 分类（classify）：证据能证明什么就从哪继续——见下表。

§3总纲：at-least-once 执行，exactly-once 记录

整套纪律一句话：提交过的活（记录的响应、记录的工具结果、提交的状态写入）绝不重跑；提交前被打断的活下个 attempt 重跑。含义：

  • 事件 hook 回调的持久效果原子提交、绝不重复，但回调里的一次外部副作用（发邮件/下单）罕见地可能发生两次——绝不能重复的事用持久状态或应用级幂等守卫。
  • 恢复后的会话总停在「下条消息能正常处理」的状态——中断的提交卡不住它后面的队列。
  • 中断留在时间线可见：aborted 半截、中断工具标记、settle 失败时的终态 advisory 信号。
guide/durability.md（Recovery after an interruption）

§4重试预算与超时：stylist 那行配置

默认 10 attempts、每提交 1 小时。按 agent 用 durability 静态覆盖：

Stylist.durability = { maxAttempts: 3, timeoutMs: 300_000 };   // stylist 实测
  • 超时是预防性的：coordinator 在唤醒节奏上监督运行中的 attempt，到点就触发 attempt 的 abort 信号——挂在 signal-aware await（provider 调用、sandbox 命令、任何工具）上的工作被解绕走正常路径 settle；忽略 signal 的 run 被抛弃而非等待。挂死最多拖「deadline + 宽限」，卡不死提交。
  • 静态在 agent 函数不跑时生效：所以 agent 自己 render 里崩溃，durability 配置仍在——不会被那次崩溃抹掉。
  • timeout 是从首个 attempt 开始的墙上总预算；turn 边界 join 和响应续接不延长它。
  • stylist 选 3 次/5 分钟的语义：购物建议 agent，宁可快速 settle failed 让用户重试，也不要挂 1 小时占着会话。

§5工具批修复：普通、durable、委派三态

工具批修复刻意保守——崩溃前已记录的结果原样保留（那些调用绝不重跑）：

  • 未决的普通调用不重跑（runtime 不知副作用做过没），settle 成显式 unknown-outcome 错误，模型看到并能反应。
  • durable:true 工具重跑，已完成 step.do 从记录回放（0005 讲过）。step 记录键到 toolCallId，跨同一调用的 attempt 携带；重新调用工具则每步全新。
  • 在途委派任务不落标记——重挂到子会话自己的持久转录，把子代理续跑完再提交真实结果；递归（孙子先续）；一批里多个任务全续完才提交批。delegate 无自己的 durability 配置——在父 attempt 下、吃父的重试预算。

合同边界：step 是 exactly-once 记录、at-least-once 执行（记录落盘的窄窗口崩溃会重跑那一步——围绕外部效果的 step 各自幂等）；redeploy 可撤回合同（恢复时若当前 render 不再声明该工具/不再 durable，则退回普通中断标记路径）。
guide/durability.md（Durable tools / Delegated tasks）

§6持久状态的原子性（再强调）

usePersistentState 写入与「做出它的那单位工作」原子提交：工具里的写入随该 turn 工具批提交、hook 里的写入随 hook 缝的检查点提交。恢复若把批判为中断，写入就没发生——重试从最后提交的状态渲染，恰好匹配模型看到的已做工作。这正是它做 at-least-once 回调守卫的根：sent 标志与发邮件的活同批提交，不可能"活回滚了标志还 true"。
guide/durability.md（Persisted state）

§7什么刻意不持久

  • 工作区状态与对话分开：会话库不存沙箱文件；虚拟沙箱易逝、恢复的 attempt 同样重建环境——被打断写入的临时文件没了。要持久工作区用按实例 id 键控的远程适配器。知识进持久状态、要留的文件进持久工作区，两者独立。
  • 在途本地 promise 不持久：awaiting 进程退出，accepted work 仍按 store 恢复，只是本地 promise 没了。想找回就把 dispatch 返回的 DispatchReceipt 持久化（如作为工作流 step 的 durable 结果），read(receipt) 从任何进程重挂。
  • agent 之外的代码不被检查点：不做「函数从最后一行续跑」。检查点边界就是 agent 本身——内部 durable 工具给可续的 step.do；外部（endpoint/脚本/cron）用平台工作流引擎，重投递 = 会话里的新 submission，持久记录显示上次完成了什么。
  • 外部副作用：flue 记录「工具跑了、返回什么」，从不记录效果本身。at-least-once 意味着边界效果可能重复——设计成幂等、键到稳定 id（toolCallId / step 名）、一次性动作用持久状态守卫。
guide/durability.md（What is deliberately not durable）

§8Node vs Cloudflare 的恢复归属

持久记录与恢复决策两目标完全相同，差在「谁拥有会话工作、接替者怎么醒来」：

  • Node：server 进程内 coordinator；lease 制——每个运行中 submission 带短 lease，owner 干活时心跳。两个触发：启动对账（接替进程 boot 时扫中断工作后台 settle，顺序保持：恢复的活排在新投递前）+ 周期 lease 扫描（快重启没等 lease 过期就被回收，秒级认领）。优雅关停：turn 边界 abort 活跃提交并等 settle。
  • Cloudflare：每个会话是 Durable Object + 自带 SQLite，归属结构性保证单活实例、无 lease 协议。恢复靠 唤醒驱动：DO 每次启动先对账上次实例在跑的 attempt；未 settle 工作存在时会自续短期 wake 调度，无人敲门也能及时恢复。
guide/durability.md（Recovery by target）

§9本课自测

本课的胜利：能一句话讲清 durability——「受理即落盘 → attempt 认领执行 → 崩溃后收敛+分类续跑 → 预算/超时到点 settle failed」，总纲是 at-least-once 执行、exactly-once 记录，不持久的是工作区文件、本地 promise、外部副作用。你写 agent 时该问的是：哪个活必须 durable:true？哪个一次性的动作要用持久状态守卫？
