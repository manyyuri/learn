§2flue 站在哪层：证据说话

0005 课的论断现在用依赖证据钉死——@flue/runtime 的 dependencies 只有两个 pi 包：@earendil-works/pi-ai 与 @earendil-works/pi-agent-core（都 ^0.83.0，和 stylist 直接装的 pi-ai 0.83.0 同一份）。逐符号看源码 import：

  • pi-ai（值 + 类型都复用）：createProvider / createModels / createAssistantMessageEventStream / clampThinkingLevel / parseStreamingJson、类型 Api/Model/Provider、isContextOverflow（compaction 分类）——provider 目录与流式运输是 pi-ai 的。
  • pi-agent-core（纯类型）：import 全是 import type——AgentMessage / AgentTool 这些消息与工具的形状借用 pi 的约定，但没有 import 它的 loop 函数。
  • flue 自建：render/frame、submission 循环、会话 append-only 流、durability、HTTP/SDK、vite 变换——这些都长在 pi-ai 的运输之上。
packages/runtime/package.json · runtime/src/（providers.ts / compaction.ts / usage.ts 的 import）· stylist-agent（pi-ai 0.83.0）

所以 stylist 里你"顺手" import @earendil-works/pi-ai 写 createProvider——那不是跨框架乱接，而是直接用 flue 自己的底层模型库。你 pi 课学的 provider 心智在这里原样生效。

同一棵树的两种摘法：coding-agent 面向「在终端里跑一个会写代码的 agent 会话」（OpenClaw 系列）；flue 面向「把 agent 当成产品里可编程、可 durable 的函数」。你两个都学了——这是很少见的双视角：既见过 pi 的 loop/资源层，又能看见 flue 在它上面怎么叠 render 与受理契约。

§5workflow-console 该站在哪层

你的 flue-workflow-console 是一个编排记录层：保存任意工作流 DSL（steps + dependsOn + skill 名），执行交给 agent（flue skill §6 明言：「Runtime 只做编排记录，真实执行交给 agent」）。用本课的轴把它钉清楚：

  • 它不该重造循环/会话/durability——那些是 flue（或 pi）已经交付的 L2。
  • 它该消费「入口即提交」的抽象：像 stylist 的 /internal/* dispatch 端点——每个工作流 step = 一次 durable submission（确定性会话 id + signal + attributes + 回执）。失败重跑 = 0009 的受理契约替你兜，不是 console 自己写。
  • skill 名解析：console 里 DSL 的 skill 是「可发现即可执行」——落在 ~/.pi/agent/skills 或项目 skills 目录的 agentskills 格式（0006 课），真正跑的时候由执行 agent 用 useSkill/读 SKILL.md 履行。你的两套生态（pi skills + flue agents）通过格式共用而互通。
  • 决策建议：若 step 的活是「给产品 agent 发 durable 任务」→ flue dispatch；若活是「起一个编码会话在仓库里改代码」→ 那更接近 coding-agent 的领地。console 站在两者之上的 DSL 层，与两家解耦、只调用执行入口——这正是它现在的设计。
flue-flow skill（Runtime 编排记录协议）· stylist-agent/flue/src/app.ts（/internal/* dispatch）· /Users/junyingli/project/AI/flue-workflow-console

§6本课自测

本课的胜利：能用一张同源图 + 一张对照表讲清两台机器——共享 pi-ai 地基，coding-agent 是命令式 harness、flue 是声明式 render harness；你的 console 站在「入口即提交」的抽象上，与两家解耦。
