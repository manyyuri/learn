flue 心智模型全景：agent 就是函数

读完这一课，你能画出一张「一次对话从消息到回复」的完整地图，并说出每一层的职责。后面每一课实现一个零件时，你都知道它装在地图的哪个位置。

你已经用 flue 做出了 stylist、Headroom、Glow 这些能跑、能部署、有 durability 与 Postgres 持久化的生产 agent——但多数是照文档拼出来的。本课先把整张地图立起来：拆开「表面能跑、说不出凭什么」的那个凭什么。这也是为什么你同时学了 pi 的架构——下面你会看到这两件事其实是一件事。

§1flue 的三句经

官方一句话定位：一个 agent 由三样东西组成——LLM、harness、专精上下文（LLM, harness, and specialized context）。harness 就是模型之外那整套"能干活"的环境：工具、技能、指令、文件系统/沙箱、会话与持久化。

flue 的关键立场是 harness-first（工具套件优先）：harness 是框架本体，不是 SDK 的一个功能。它给你两个原语来组装 agent：

  • agent 函数（agent function）——返回系统指令的函数；
  • hook（hook）——在函数体内调用、声明能力的 use*。

其余所有难事（持久化、恢复、会话、重试）是运行时替你兜的 durability——不用你写恢复管道。
guide/why-flue.md（Harness-first / Durable）· guide/building-agents.md（What is an agent）

这句话你其实早就"直觉到"了：stylist 里 Stylist.durability = { maxAttempts: 3, timeoutMs: 300_000 }、Headroom 里 @flue/postgres——你在用 durability，只是还没能说出它凭什么成立。那是第 9 课。

§2核心心智：agent 就是函数

flue 里 agent = 一个返回字符串的普通函数，返回的字符串就是它的系统指令（system prompt instructions），会连同对话历史一起交给 LLM。

最反直觉也最重要的一点：这个函数每个 turn 都会重新执行——每次要调用模型前，flue 都会把你的函数再跑一遍、从零重建指令，所以返回的字符串永远反映当下状态。官方明说：把它想成 React 组件的 render，这并非巧合，agent 函数就是照 React 模型设计的。
guide/building-agents.md（"The agent function re-renders on every turn"）

agent 函数普通函数 · 每次模型调用前重跑（render）
↓ 体内调用 hooks，能力登记到「渲染帧」
hook 层useModel / useTool / useSkill / useSandbox / …
↓ 函数 return
系统指令+ 帧上收集的 模型·工具·技能·沙箱·子代理 配置
↓ 提交给 LLM 工具循环
模型调用 → 工具执行 → 重渲染 → …直至最终回复

所以 hooks 与 React 的 hooks 共享同一纪律：只能在 render 期间调用；调用顺序即收集顺序；能力可以条件增减（比如"升级后才有退款工具"），框架会替你把工具集的变化通知给模型。区别于 React 的关键一点：hook 数量可以随渲染变化。

§4一次消息的旅程

把六层塔串成时间线。假设你的 Headroom 收到一条「今天太累了」：

① 进入POST /agents/headroom/demo-user · 或 dispatch / flue run · L6
↓ 受理
② 记为一次 submission 并落会话日志可重放——断线也不丢 · L5
↓ 首渲染
③ 跑 agent 函数hooks 登记 模型/工具/指令 → 得「调用配置」· L2–L4
↓ LLM 工具循环
④ 模型调用 → 要工具？→ 执行工具 → 重渲染反映状态 → 再来至最终回复 · L4
↓ 收尾
⑤ 回复与数据 parts 写回会话客户端经投影流式收到 · L5→L6
  1. 进入：入口五花八门，但都走同一条 agent + durability API，区别只在「运行时怎么起、有没有 HTTP 服务器」（guide/building-agents.md「Interacting with your agent」）。
  2. 受理即持久：被接受的工作（submission）先落日志，这是 durability 的支点。
  3. 首渲染：运行时调 renderAgentFunctionWithStructure(agent, …)，函数在渲染帧内执行，hooks 把模型、工具、技能、指令落到帧上，返回「调用配置」。
  4. LLM 工具循环：模型按「历史 + 指令」回答；若它请求调工具，运行时执行工具、把结果回填，然后重渲染（让函数看到新状态）再进下一轮。
  5. 回复与流：最终回复（含文本与 data parts）写回会话；客户端通过会话投影流式读到。
runtime/src/client.ts（submission 首渲染 + 每轮重渲染）· runtime/src/hooks/render.ts · guide/agent-hooks.md（Event hooks）
第 ② 步「受理即持久」和第 ④ 步「每轮重渲染」是本课最该记住的两个机制事实——前者是 durability 的根，后者是「agent 即函数」的真正含义。它们分别在第 9 课和第 2 课被彻底拆开。

§5隐藏主线：flue 建在 pi 之上

官方 why-flue 有一句不显眼但重磅的话：“Flue builds on Pi, the open agent harness behind OpenClaw, and integrates it deeply into every agent you build.” 你在 pi-coding-agent 工作区深潜过的那台机器，正是 flue 的地基。

源码证据（packages/runtime/package.json）：@flue/runtime 依赖 @earendil-works/pi-ai ^0.83.0 与 @earendil-works/pi-agent-core ^0.83.0。grep 全源码会发现：

  • 复用 pi 的模型/provider 层（pi-ai 的流式运输、Usage）与消息/工具类型（AgentMessage、AgentTool）——flue 归一化后包装成自己的公开类型（usage.ts 把 pi-ai 的 Usage 转成 PromptUsage；provider-diagnostics.ts 读 pi-ai 的 AssistantMessage）。
  • 自建 render/frame、会话、durability、HTTP/SDK、vite 变换——这些是 flue 自己的机器。
guide/why-flue.md · packages/runtime/package.json · runtime/src/usage.ts
这解释了一件你可能有过的困惑：stylist 里你直接 import @earendil-works/pi-ai@0.83.0 来桥接——那不是"跨框架乱接"，而是摸到了 flue 自己的底层模型库。第 13 课（案例课）会完整复盘这套桥接。
