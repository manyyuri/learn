运行时与部署：四种入口，一条 durable 管线

读完这一课，你能把六层塔的 L6 打开：CLI / HTTP / dispatch / init·start 四种入口怎么殊途同归到同一条 submission 管线，以及 conversation URL + SDK 是怎么消费部署态的。

§0开场检索

§1一个论断：入口多样，管线唯一

0001 地图说过：入口五花八门，但都走同一条 agent + durability API，区别只在「运行时怎么起、有没有 HTTP 服务器」。四种入口：

入口场景怎么起
CLI flue run本地直接跑一个 agent 模块不起服务器、不构建应用；对话跨运行持久
HTTP（createAgentRouter 挂载）部署态服务对话POST 即发即收（202），回复从 GET/流读
dispatch()异步事件进 agent（webhook/队列/chat）接受异步处理，立即返回回执
start() / init()自己 Node 进程内引导（cron/脚本/测试）start({agents, db}) boot 运行时 → init 拿句柄
guide/building-agents.md（Interacting with your agent）

§2HTTP 挂载：app.ts 是路由图

flue 从不自动挂载 agent。注册（'use agent' 扫描）让 agent 在应用里可寻址；HTTP 服务是你在 app.ts 路由图里的显式决定。默认导出就是服务器——每个 agent/channel/自定义路由都在那显式挂载，不从文件名/目录约定生成。

const app = new Hono();
app.route('/agents/hello', createAgentRouter(Hello));
export default app;

几个性质：URL 是你的（/agents/<name> 只是惯例）；挂载路径不是身份（会话按 durable identity 键控，非 URL——挪挂载点不用迁移数据）；createAgentRouter 是无副作用纯工厂（模型/durability/initialData schema 全在 agent 模块上声明，不在挂载点）；挂载是暴露决定，不是注册（注册了没挂的 agent 走不了 HTTP，但 dispatch/schedule 仍可驱动它）。Hono 是惯例不是必须——默认导出只需 fetch 兼容形状。
guide/routing.md（app.ts is the route map / Mounting an agent）

§3conversation URL：一次对话一张 URL

每个会话在挂载路径 + 你选的会话 id 处：/agents/support/ticket-8472（id 由调用方选，首条消息到达时创建会话）。router 服务的表面：

Route作用
POST /:id投递一条消息（202 受理）
GET /:id读会话（快照 / updates / 实时流）
HEAD /:id读流元数据
POST /:id/abort中止在途与排队工作
GET /:id/attachments/:id下载附件字节
  • 发送是 fire-and-forget：消息durably 受理后立刻 202，agent 还没跑。响应带坐标：streamUrl、resume offset、submissionId。这条路由没有 wait-reply 模式——回复落在会话里，从那儿读。
  • 读会话：普通 GET = 一次物化快照；?view=updates&offset=… 用 long-polling 或 SSE 连续流。
guide/routing.md（The conversation URL）· runtime/src/runtime/handle-conversation-routes.ts

§4SDK：包住整个表面

createFlueClient({ url }) 一个客户端只地址一个会话 URL，把整张表面打包：send() / wait()（从 settled 记录 resolve/reject）/ observe() / history() / abort() / attachmentUrl()。SDK 的 send 同样 fire-and-forget；wait 在 waiters 侧重连后仍能观察到终态（靠 submission_settled 记录）。stylist 的部署面正是 @flue/sdk 消费 vite+hono 起的服务。
guide/routing.md（The SDK wraps this surface）· packages/sdk/src/public/* · stylist-agent/flue（@flue/sdk）

§5dispatch 与 init：服务端/脚本侧的驱动

  • dispatch(Agent, { id, message })：异步事件（webhook 验签后）进 agent——你选会话，它异步处理并立即返回 DispatchReceipt。useDispatchMessage() 是绑定到本实例的版本。只在 dispatch 用的 agent 甚至无需挂载。
  • start() / init()：脚本里 await using flue = await start({ agents:[Reporter], db: sqlite('./nightly.db') }) boot 运行时 → init(Reporter, {id}) 拿实例句柄 dispatch()/read()。db 选项决定对话是否活过脚本：省略 = 仅内存。start() 不走构建、不吃 db.ts——直接传适配器。
guide/building-agents.md（dispatch / Standalone scripts）· runtime/src/agent-client.ts · runtime/src/dispatch-queue.ts

§6flue run 的引导：一条无 HTTP 的真管线

run-bootstrap 源码注释值得抄一段：「flue run 引导走的是真实的 durable submission 路径——共享的 runtime 装配（注册、持久化 connect/migrate/validate、coordinator）、durable 直接受理、从 canonical 会话流经观察缝看 settle。不创建任何 HTTP：无 Hono app、无 listener、无 channels。」

两处工程细节（解释"为什么这么重"）：bootstrap 由同一个非监听 vite server 加载（与 agent 模块同图）——保证执行图里每个 @flue/runtime 解析到同一份磁盘拷贝（runtime 有模块级注册表：providers/agent 注册/instrumentation，第二份拷贝会静默拆散状态）；无 db.ts 时用 sqlite() 指向 run.db，永不重置——所以 --id 能跨调用续会话。
packages/cli/src/lib/run-bootstrap.ts · packages/cli/src/lib/run-local.ts · guide/database.md（flue run 缓存）

§7本课自测

本课的胜利：一句话串起 L6——flue run 起无 HTTP 的真管线、app.ts 显式挂 createAgentRouter 给每个会话一张 URL（POST 受理 / GET 读流）、dispatch 从服务端异步驱动、start/init 在脚本内引导、SDK 把整张会话 URL 表面打包给你。殊途同归到同一条 durable submission 管线。
