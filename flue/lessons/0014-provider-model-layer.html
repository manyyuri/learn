provider 与模型层细节：Models 单例、usage 归一化、诊断通道

读完这一课，你能说出模型层三个内部件的分工——运行时怎么持有/注册 provider、pi-ai 的 usage 怎么被归一化、provider 边界的信息怎么穿透到观测——并据此排障。

§0开场检索

§1Models 单例：模块级、按 id 替换

运行时持有一个模块作用域的 pi-ai Models 实例（createModels()），由 app.ts 与生成的服务入口在模块初始化时填充。四个操作：

  • setProvider(provider)——注册一个 pi-ai provider；每次调用替换同 id 的前一个，不累积。任何 Provider 都行：内置工厂、createProvider(...)、测试假 provider。Cloudflare 上在 app.ts 注册 cloudflare provider 会压过生成的 Workers AI 默认。
  • hasProvider(id)——查是否已注册。
  • getRuntimeModels()——内部取用（Session 的流式/补全调用）。
  • resetModelsForTests()——整体换新（仅测试）。

凭证走每个 provider 自己的 auth 声明：Node 读 env，Cloudflare 经 nodejs_compat 的 process.env。
runtime/src/runtime/providers.ts

「模块级单例」解释了 0011 课 run-bootstrap 为什么费劲保证「同一份磁盘拷贝」——两副本会各自持一个 Models 实例，provider 注册被静默拆散。

§2内置 provider 注册：把 pi 的导出名挡在生成代码外

生成的 server 入口注册内置 provider 时，是从 @earendil-works/pi-ai/providers/<id> 模块命名空间里挑出工厂再注册——注释道破原因：这样 pi 的精确导出名（anthropicProvider、azureOpenAIResponsesProvider…）就不进生成代码，pi 改名不会从生成代码底下漂走。这也呼应 0004 课 flue({providers:[...]}) 的穷尽式列表——列表只决定「生成代码 import 哪些 namespace」。
runtime/src/runtime/builtin-providers.ts

§3usage 归一化：解耦才是目的

usage.ts 的注释直白：把 pi-ai 的 Usage 转成 flue 公开的 PromptUsage。「两者今天结构相同，但走归一化让 flue 的公开类型与 pi-ai 解耦——pi-ai 未来加字段不会漏进 runtime 的公开面」。内部工具：

  • emptyUsage()——全零（加法单位元）。
  • addUsage(a,b)——逐字段求和，含嵌套 cost；返回新对象不改入参。
  • fromProviderUsage(u)——pi-ai Usage → flue PromptUsage；输入 undefined 返回 undefined。

这些被 prompt()/skill()/task()/compaction 用来把 token + cost 数字逐调用聚合，compaction 持久化路径在落 canonical 压缩记录前先归一化。
runtime/src/usage.ts

§4诊断通道：provider 归一化丢了什么，就补什么

provider-diagnostics.ts 的存在理由值得整段读：provider 会归一化它们收到的东西——原始 SSE finish_reason 变成 pi-ai stopReason、响应头被读后丢弃、body 被摊平成 errorMessage 散文。于是每次观测需要某个「归一化前的值」时，就冒出临时通道（消息字符串标记、对散文跑正则）。这个文件是响应路径唯一官方替代：

在归一化边界，别丢归一化前的值——把它挂在这里，经显式 allowlist 投影到观测。
  • 运输是 pi-ai 自己的扩展点：AssistantMessage.diagnostics 随消息走，复制不丢、无需旁路通道。
  • 投影有 allowlist：ProviderResponseDiagnostics 只列少数字段（归一化前的 providerFinishReason、Cloudflare 网关日志 id cf-aig-log-id…），会话只把这些投影到 turn 观测——绝不任意带 headers/payload（可能含凭证）。
  • 纯遥测：不参与重放、执行身份、归一化的 stopReason/finishReason 契约。
  • 抛错路径（请求在出消息前就死）用不了这通道，仍靠消息标记如 RETRYABLE_INTERRUPTION_MARKER——直到 pi-ai 长出结构化错误字段。
runtime/src/provider-diagnostics.ts

§5元数据驱动的语义闭环（回顾 + stylist 复盘）

0004 课讲过 catalog 条目带元数据，现在能补全「谁消费它」：contextWindow → 阈值 compaction 触发点；reasoning → thinkingLevel 是否上 wire（false 则静默丢弃）；input → 能否收图（无则图换 "(image omitted)" 占位）；cost → usage 聚合计价。stylist 注册表里那几行不是摆设——reasoning:false（DeepSeek 关 thinking 提速）、contextWindow:1_048_576、vision input:['text','image'] 直接决定它 agent 的 compaction 与多模态行为。

§6排障语义：错误发生在哪层

  • Provider is not configured: anthropic——Models 单例里没这个 id 的 provider（没配密钥 / providers 穷尽列表没含它 / 没 setProvider 自定义）。
  • 未知 specifier —— 请求发出前 fail fast，报 unresolved provider + model id。
  • 瞬时 provider 错误（限流/宕机）——退避重试 turn，走 0009 的错误预算。

§7本课自测

本课的胜利：模型层 = 模块级 Models 单例（setProvider 按 id 替换）+ usage 归一化解耦 + diagnostics allowlist 通道三件套；元数据驱动 compaction/thinking/模态，错误三层分诊（未配置 / 未解析 / 瞬时）。
