案例课：stylist-agent——一座双层架构

读完这一课，你能用前 11 课的心智模型拆开你自己的 stylist：provider 桥接、最少权限 agent、durable 工具、双层校验、dispatch-only 端点——以及它们为什么这么配。

§0开场检索

§1项目拓扑：一座双层架构

stylist 不是一个"纯 flue 应用"，而是两套运行时共享同一份业务代码：

stylist-agent/
├─ server/            ← 你原来的业务服务（Express）
│  ├─ config.ts         config.json + ~/.pi/agent/models.json 读密钥
│  ├─ tools.ts          【业务工具注册表】11 个工具：Zod schema + 真实 handler + 规则引擎
│  ├─ ootd.ts / rules.ts / plans.service.ts / …  业务逻辑
│  └─ index.ts / routes/ / scheduler.ts / llm.ts   老的服务面（聊天/上传/cron）
└─ flue/              ← 本课解剖的 flue 子工程
   ├─ vite.config.ts    flue() 插件
   ├─ src/app.ts        provider 注册 + 3 个 router + 2 个 dispatch-only 端点
   └─ src/agents/       3 个薄 agent（stylist / daily-outfit / photo-review）
       + src/tools.ts   flue 侧工具适配器（valibot schema + 委托 server 注册表）

关键点：flue 把 import 的 server 模块打包进 flue/dist，但 config.ts 特意优先读进程工作区的 config.json——让两套运行时读同一份配置与数据目录（server/config.ts 头注释）。

§2provider 桥接：pi-ai 的 createProvider 直进 flue

app.ts 顶部的 setProvider(createProvider({ id:'opencode-luna', … }))——这正是 0004 课「Custom providers」的实盘。你要点不是"注册了个模型"，而是：

  • provider 是 pi-ai 自己的对象，flue 直接收：因为你 import 的 @earendil-works/pi-ai 与 @flue/runtime 内部依赖的 pi-ai 是同一份 0.83.0（第 13 课展开）。
  • 模型元数据深思熟虑：reasoning:false（DeepSeek 关 thinking 提速）、compat.thinkingFormat:'deepseek'（reasoning_content 流）、contextWindow:1_048_576、vision 模型 input:['text','image']。runtime 就靠这些决定 compaction 阈值、thinking 是否上 wire、能不能收图。
  • 密钥解析 apiKey.resolve() 走 server/config.ts：env（GLM_API_KEY/ZHIPU_API_KEY）> ~/.pi/agent/models.json 的 opencode-luna apiKey——你把 pi 生态的模型配置当成了 flue 的凭证源，两套 agent 系统共享一套 key 治理。
stylist-agent/flue/src/app.ts · server/config.ts（opencodeLunaApiKey）

agent 侧只要 useModel('opencode-luna/deepseek-v4-flash-vision-exp')——specifier 解析到你在 app.ts 注册的 provider。没这步注册，跑起来就是 0004 课那句 Provider is not configured。

§3agent 组织：薄函数 + 最少权限 + 参数化注册器

三个 agent 每个只有 14–27 行：useModel + 调注册器选工具 + 返回指令。这是 0005 课「没挂载的工具模型根本调不到」的刻意运用——按任务面分配最少工具：

// daily-outfit.ts —— 只读 3 个 + 1 个 durable 写
registerBusinessTools(['get_profile','query_wardrobe','get_weather']);
registerDurableBusinessTools(['generate_outfit']);
DailyOutfit.agentName = 'daily-outfit';
DailyOutfit.durability = { maxAttempts: 3, timeoutMs: 120_000 };

registerBusinessTools(names[]) 是参数化的自定义 hook（体内批量调 useTool）——0003 课自定义 hook 的实盘：把「schema 表 + 委托 execute」抽成可复用注册器。循环里按 name 查本地 valibot schema 与 server 注册表，找不到就抛（fail fast）。agentName 钉住身份（改名不迁移库）。
stylist-agent/flue/src/agents/daily-outfit.ts · src/tools.ts

§4durable 工具：step.do 用得对

看注册器的 durable 分支——这是 0005/0009 课规则的教科书式执行：

useTool({
  name, input: schema,
  description: `${tool.description} 这是写操作，必须安全重试。`,   // ← 语义写给模型
  durable: true,
  async run({ data, step }) {
    const output = await step.do(`${name}:${JSON.stringify(data)}`, () => execute(name, data));
    return { output };
  },
});
  • 名字确定性：`${name}:${JSON.stringify(data)}`——同参数重试解析到同一 step，回放不重跑；绝无随机/时间。
  • 写操作 = durable：generate_outfit / log_outfit_feedback / create_photo_plan / review_photo_session 归到写分支；读操作走普通工具（中断 settle unknown，让模型重试读无害）。
  • description 把语义给模型：「这是写操作，必须安全重试」——模型看到的是可理解的行为约定，不是实现。
  • durability 逐 agent 配：daily-outfit 120s（轻任务快失败）、photo-review 600s（复盘跑得久）、stylist 300s。三档 timeout 都是「宁快失败让人重试」的 0009 决策。

§5双层校验与防编造：机制级 anti-hallucination

server/tools.ts 的注册表注释把架构意图说得很透：每个工具保留 Zod 参数校验与真实业务 handler；flue adapter 把模型参数交给这里做第二层校验，「确保模型不能绕过规则引擎编造衣橱数据」。关键原则：

所有涉及真实数据（衣橱/档案/穿搭）的操作都只能通过工具完成——模型拿到的永远是工具返回的事实，从机制上杜绝编造单品 ID。

对应 0005 §7「参数不是授权边界」：不让模型选它不能选的值（客户/数据范围由 trusted 代码定），stylist 把它升级成「模型根本不接触数据源，只碰工具的返回值」。flue 侧 valibot schema 是给模型看/首层校验，server 侧 Zod 是真校验——双 schema 是这套机制的代价（可后续统一）。
server/tools.ts（注册表头注释）· src/tools.ts（valibot 镜像）

§6交互面：三种入口各司其职

  • createAgentRouter ×3：/stylist、/daily-outfit、/photo-review——给互动对话（聊天/多轮）用。
  • dispatch-only 内部端点：POST /internal/daily-outfit / /internal/photo-review——给老 Express 服务与 cron 用。看它怎么选会话 id：id: \`daily:${date}\`、id: \`photo-review:${planId}\`——确定性 id = 天然幂等键：同一天重投递续同一会话，不重复生成。消息是 signal（结构化事件，带 attributes），202 受理即回——0009 课「受理契约」的实盘。

§7复盘：哪些决策与课程心智模型严丝合缝
