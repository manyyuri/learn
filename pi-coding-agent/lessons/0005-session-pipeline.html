Session 深潜：一条 prompt 进门后、进 agent 前

第 1 课我们看到了旅程，但 session.prompt(text) 在把消息交给 agent.prompt 之前，还有整整一条前处理管线。这一课把 agent-session.ts 里 prompt() 方法逐段拆开。

本课成果：能说出 prompt() 前处理的每一步顺序及其目的——这对你的 workflow 很重要：你以为发出去的就是那句话，实际它可能先被当成命令、被 skill 块改写、被扩展拦截、被 auth 校验拦下。

1. 管线全景（源码核实，按真实顺序）

调用 session.prompt(text, options) 后，依序发生：

#检查 / 动作若命中
1/xxx 开头？→ 查扩展命令命令立即执行（哪怕在流式），不进入 agent
2压缩进行中？抛错拒绝新 prompt
3扩展 input 拦截可 handled（吞掉）或 transform（改写文本/图片）
4展开 /skill:name 块 与 prompt 模板 /name文本被替换为展开内容
5正在流式？必须有 streamingBehavior，否则抛错；走 steer/followUp 队列
6冲刷挂起的 bash / 自定义消息并入本次提交
7校验已选模型无模型 → 抛 No model selected
8校验认证（hasConfiguredAuth / checkAuth）无 key → 抛错（OAuth 过期有专门文案）
9压缩检查（catch 上次被 abort 的残留）需要 → 先压缩再发
10组消息：user 消息 + 挂起的 nextTurn 消息 + 扩展 before_agent_start 注入的 custom 消息应用扩展改写的 systemPrompt
11preflightResult(true) → _runAgentPrompt(messages)真正进入 agent
记住第 5 步：流式期间 prompt() 没有 streamingBehavior 会直接抛错——这是 single-flight 约束在上层的体现（第 1、2 课）。

2. 跑起来之后：run + 后处理循环

_runAgentPrompt(messages) {
  this._isAgentRunActive = true;
  try {
    await this.agent.prompt(messages);
    while (await this._handlePostAgentRun()) {   // ← 后处理
      await this.agent.continue();
    }
  } finally {
    // 清理 override、冲刷消息、发 agent_settled
    await this._emitAgentSettled();
  }
}

_handlePostAgentRun() 决定要不要再 agent.continue() 一次，按序判断：

  1. 最后一条助手消息可重试错误？→ 走 _prepareRetry（自动重试）
  2. 该压缩？→ _checkCompaction（第 6 课详述）
  3. agent_end 扩展处理器排队了消息？→ agent.hasQueuedMessages()

三者任一命中就 continue() 再跑一轮。全部否定 → finally 里发 agent_settled。这就是你在第 1 课看到的 agent_settled 的真正出处——它总是在 retry/compaction 决策做完之后。

3. 事件转发与持久化（_handleAgentEvent）

session 订阅了 agent 的事件（构造时 this.agent.subscribe(this._handleAgentEvent)）。每个 agent 事件到达时：

  1. 先清队列记账：若该 user 消息来自 steer/followUp 队列，从 session 侧的队列快照移除并发 queue_update（保证 UI 看到最新队列状态）
  2. 扩展先听：_emitExtensionEvent(event) 把事件广播给扩展
  3. 再广播给订阅者：agent_end 会额外附上 willRetry 标记
  4. 持久化：message_end 时把消息写进 SessionManager——custom → appendCustomMessageEntry；user/assistant/toolResult → appendMessage；assistant 消息同时被记录为 _lastAssistantMessage 供后处理用

这个顺序解释了订阅者的一个直觉陷阱：扩展和订阅者看到的都是转发后的同一批事件，但持久化在 message_end 才发生——所以「订阅到事件」不等于「已落盘」。

4. 对你 workflow 的三条启示

  • 「发一句话」可能是多条消息：user 消息 + 挂起的 custom 消息会被一起提交。扩展在 before_agent_start 里注入的消息，会先于你这句话被模型看到。
  • auth 错误是同步前置检查：没 key 时 prompt() 抛的是「你没配好」而不是让模型跑完报错。你可以在步骤开始前用 modelRuntime.getAvailable() 预检，给出干净的错误页。
  • 命令/模板扩展发生在最前面：如果你的 workflow 提示词以 / 开头且被注册成命令，它根本不会走到 agent——这既是功能也可能是坑。
