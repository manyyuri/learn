工具系统：定义、校验与执行

你在 SDK 里用 defineTool 声明过自定义工具，也知道读文件会走到 read 工具。这一课看清工具的一生：从「定义」到「被模型点名」到「参数校验」到「执行并把结果回灌」。

本课成果：弄清 AgentTool 的完整结构、参数校验发生的准确位置与方式、并行/串行执行的决策逻辑，以及「工具工厂」（createReadTool 等）为什么做成可注入 operations 的形式。

1. 两种表现形态：定义 vs 运行时

工具在系统里有两个名字，别搞混：

形态是什么出现位置
ToolDefinition“定义优先”形态，execute 会额外拿到扩展上下文 ctx扩展注册、工具工厂的 createXToolDefinition
AgentToolagent 循环实际消费的形态被塞进 state.tools、进入 Context.tools

两者用 wrapToolDefinition() 互转（coding-agent/src/core/tools/tool-definition-wrapper.ts）。内置工具的 createReadTool(cwd) 其实就是 wrapToolDefinition(createReadToolDefinition(cwd))——一条线下来。

2. AgentTool 的结构（源码核实）

interface AgentTool extends Tool {
  name: string;               // 模型点名用的标识：如 "read"
  label: string;              // UI 展示名
  description: string;        // 给模型的说明
  parameters: TypeBoxSchema;  // JSON schema，用于校验
  prepareArguments?: (args) => args;      // 校验前的兼容垫片
  execute(toolCallId, params, signal?, onUpdate?): Promise<AgentToolResult>
  executionMode?: "sequential" | "parallel";  // 逐工具覆盖默认策略
  replay?: "never" | "safe";  // 效果可重放性（重试相关）
}

execute 返回 AgentToolResult，核心字段：content（给模型的文本/图片）、details（给 UI 的结构化数据）、terminate（提示本批后停止）。onUpdate 回调可在执行中流式吐 partial 结果，对应你订阅到的 tool_execution_update。

规则：execute 失败用 throw 表达（循环会包成错误 toolResult 回给模型），不要吞错。返回的 content 最终成为 toolResult 消息正文——就是第 1 课第 7 步那份东西。

3. 参数校验发生在执行前

校验不在工具代码里，而在循环的「准备阶段」（agent-loop 的 prepareToolCall），真正实现是 pi-ai/src/utils/validation.ts 的 validateToolArguments：

args = structuredClone(toolCall.arguments);
normalizeOptionalNulls(args, schema);   // 规范化 null/缺省
Value.Convert(schema, args);            // typebox 类型转换/强转
validator.Check(args) ?? 抛出格式化错误;

校验失败 → 异常 → 该 toolCall 拿到一条 isError 的 toolResult，模型下回合会看到错误原因并自行纠正。TypeBox schema 是参数合约的唯一事实来源（内置工具的 readSchema 就是 Type.Object({ path: Type.String(...), offset: Type.Optional(...) })）。

4. 执行：并行还是串行

一个助手消息可能带多个 toolCall。执行策略判定（agent-loop.ts 的 executeToolCalls）：

  • 默认 parallel：工具并发执行；tool_execution_end 按完成顺序发，toolResult 消息按原声明顺序补发。
  • 若 config.toolExecution === "sequential" 或本批里某个工具声明 executionMode: "sequential" → 整批改串行，逐个来。
  • 特殊安全阀：stopReason === "length"（输出被 token 上限截断）→ 整批工具直接判失败，因为截断的 JSON 参数可能不完整，宁可让模型重发。

另有两个钩子夹在中间（第 2 课讲过）：beforeToolCall（拦）与 afterToolCall（覆盖结果）。

5. 内置工具为什么是「工厂 + operations」

看 read.ts：真正的文件读取被抽象成 ReadOperations 接口（readFile/access/detectImageMimeType），默认实现是本地 fs，但你可以注入自定义 operations——官方注释写明这是为了「委托给远程系统（例如 SSH）」。同理 bash 有 BashOperations。

这意味着：内置工具的可测性、可替换执行后端是设计出来的，不是偶然。你在自己的 workflow 里若想把「读文件/跑命令」落到沙箱或远端，不用重写工具，注入 operations 即可。

工具清单（tools/index.ts 的 allToolNames）：read, write, edit, bash, powershell, grep, find, ls。SDK 里 tools: [...] 是一个 allowlist——只声明名字，session 会用它去工厂取对应工具。
