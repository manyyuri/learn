一条 prompt 的完整旅程

你在自己的工作流应用里写过 session.prompt("…")，也 session.subscribe() 收过事件。这一课把那个黑盒拆开：一次 prompt 究竟经历了什么，为什么你会看到那些事件。

本课成果（20 分钟内）：能画出一张图，说清「prompt → N 个回合 → agent 结束」的全过程、每个环节的职责，以及事件是在哪一拍发出的。

0. 从你已经会的东西出发

你在 SDK 层看到的典型代码是三层：

const { session } = await createAgentSession({ … });
session.subscribe((event) => { … });   // 收事件
await session.prompt("从需求澄清开始");  // 发一条 prompt

对此刻的你来说，prompt() 是黑盒、事件是「会来但顺序记不住」的东西。这一课之后，你会看到黑盒里其实只有一套很干净的机器。

2. 核心心智模型：一次 prompt = 一串「回合」(turn)

最容易误解的一点：一次 prompt() 不是一次 LLM 问答，而是一串回合，直到「没有更多事要做」。

定义：一个 回合 (turn) = 一次「LLM 返回一条助手消息」的过程。助手消息里如果带了 toolCall，就得执行工具、把结果放回上下文、再来一个回合吃结果。

循环有两个「为什么还要再来一回合」的来源：

  • 内层（工具结果）：刚结束的回合带了工具调用 → 必须再来一回合吃工具结果。这是工具循环的主体。
  • 外层（followUp 队列）：agent 本来要停了，但 follow-up 消息排队了 → 再开一批回合。这是 session.followUp() 的落点。
       一轮 run（一次 prompt / 一次 continue）
       ┌──────────────────────────────────────────────┐
  ┌────▼────┐   带 toolCall?     ┌─────────────────┐  │
  │ 调 LLM  ├────是─────────────►│ 执行工具(们)     │  │
  │ 得助手消息│                    │ 结果→toolResult  │  │
  └────┬────┘                    │     消息入上下文  │  │
       │ 否                       └────────▲────────┘  │
       ▼ 无工具调用                         │是        │

       │                                             │
       ▼ followUp 队列非空? ──是──► 再开一批回合 ──────┘
       ▼ 否
    agent_end（run 结束）
       ▼
  session 后处理: retry? → compaction? → 收尾 → agent_settled

3. 一次具体旅程：让它读文件

假设 agent 收到 prompt：“看看当前目录有什么文件”，它决定调用 ls 工具。这是从源码里读出来的真实时序（文件：agent-loop.ts 的 runLoop、agent-session.ts 的 prompt/_runAgentPrompt）：

#谁做了什么订阅者看到的事件
1sessionprompt()：展开命令/模板 → 校验 model+auth → 检查 compaction → 拼好 user 消息 → agent.prompt(msg)—
2agent把新消息推入上下文，开始 runLoopagent_start · message_start/end（user 消息）· turn_start
3agent上下文 convertToLlm → 调 streamFn(model) 请求模型—
4model流式返回：说“我用 ls”，并声明 toolCall lsmessage_update（text_delta、toolcall_*）
5agent助手消息完整、内含 1 个 toolCall → 执行阶段message_end
6agent→tools找到 ls 工具，校验参数，执行tool_execution_start → tool_execution_update（流式输出）
7agent把工具输出包成 toolResult 消息，推入上下文tool_execution_end，随后 toolResult 的 message_start/end
8agent该回合带工具调用 → 继续内层循环，带工具结果再调一次模型（第 2 回合）turn_end → turn_start
9model基于工具结果返回最终答案（无 toolCall）message_update（text_delta）
10agent无工具调用、无排队消息 → run 结束message_end · turn_end · agent_end
11session后处理 _handlePostAgentRun：需要 retry？需要 compaction？都没有 → 收尾agent_settled

注意第 8 步是关键转折：工具结果不是“额外回报给用户”，而是变成一条消息塞回上下文，让模型在下一回合看到它。你订阅时看到的那一串 turn_start/turn_end，就是第 2 回合、第 3 回合……的边界。

4. 事件发生在哪一拍

session.subscribe() 收到的 = Agent 核心事件（去掉 agent_end 后）再加上 session 自己的事件。对照起来记：

事件在哪一拍发出来源层
agent_start / agent_end一次 run 的开头 / 结尾agent
turn_start / turn_end每个回合边界（一次 run 内可能有多个）agent
message_start / message_end每条消息（user / 助手 / toolResult）进入与定型agent
message_update助手消息流式增量（文本/思考/工具声明）agent
tool_execution_start/update/end某个工具调用的执行前后agent
agent_settledrun 真正结束、包括 retry/compaction 决策做完之后session
queue_updatesteer/followUp 队列变化session
auto_retry_start/end · compaction_start/endsession 在 run 之间做的重试 / 压缩session

一句话帮你记忆：「turn 和 message 是 agent 在跑；settled、retry、compaction 是 session 在操心。」把事件归到“谁在发出”，你的代码就能写对——比如“整个 run 彻底结束”该等 agent_settled，而不是 agent_end（agent_end 之后 session 可能还要 retry/compact）。

5. 三个反直觉的设计洞见

① Agent 是「单飞」的（single-flight）

一个 Agent 同时只跑一个 run（源码里 activeRun）。所以 正在流式时再调 prompt() 会直接抛错——你必须走 steer()（插话）或 followUp()（等它停再说）。这解释了你在 SDK 文档里见过的 streamingBehavior 选项：它不是锦上添花，是这条约束逼出来的。

② 上下文就是「消息序列」，工具结果也是消息

模型看到的一切 = state.messages（+ systemPrompt + tools）。工具执行的产出不是旁路数据，而是被包成 toolResult 角色消息，成为下一回合上下文的一部分。你自定义工具时返回的 content，最终就是进入这里的一段文本。

③ Session 是 Agent 的监护人，不是 Agent 本身

命令展开、skill 块、prompt 模板、auth 校验、自动重试、压缩、事件里的 agent_settled——全在 session 层，不在 agent 层。Agent 核心只干一件事：对着当前 state 跑到没活干。这个边界意味着：如果你想把 pi 的循环嵌进一个很自定义的宿主，你复用的是 Agent/runAgentLoop；如果你想要开箱即用的全部照料，你用 AgentSession。
