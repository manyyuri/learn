持久化与 SessionManager：会话是一棵树

会话不只是一长串聊天记录——pi 把它存成 JSONL，并且用 id/parentId 组织成一棵可以原地分支的树。这一课弄清磁盘格式与树 API，你会明白「为什么能无文件地 fork / 回溯」。

本课成果：能读懂一份 session JSONL、说清「叶子(leaf)」与「路径(path)」的含义，并会用 SessionManager 的树操作（branch / createBranchedSession / label）——这些是你 workflow 里做「检查点、回滚、多方案分支」的底层能力。

1. 磁盘格式（docs/session-format.md 核实）

~/.pi/agent/sessions/--<路径>--/<时间戳>_<uuid>.jsonl

每行一个 JSON 对象，带 type 字段；首行是 header（含版本号）。条目类型：message（含 user/assistant/toolResult/custom 各类）、thinking_level_change、model_change、compaction、branch_summary、custom、label、session_info。版本：v1 线性 → v2 引入 id/parentId 树 → v3 把 hookMessage 改名 custom；加载时自动迁移到 v3。

「你删了就没了」：删会话 = 删对应 .jsonl。没有中央数据库——会话就是这些文件。

2. 关键心智模型：leaf 与 path

  • 当前会话 = 从根走到某个「叶子」(leaf) 的一条路径。条目通过 parentId 串成树。
  • 对话继续 = 在叶子后 append 新条目。
  • 分支 (branch) = 把叶子移到更早的条目，之后 append 的新条目就成为它的一条新孩子——同一文件里长出两条分支，互不新建文件。
  • 文件的「有效内容」永远是当前 leaf 那条路径，而不是整棵树。所以「getPath()（根到当前叶）才是上下文来源」。
推论：为什么 append-only + leaf 指针？因为回溯/分叉不需要复制文件——只要把 leaf 指回去。代价是文件里会累积「被放弃的分支」，所以需要 branch_summary（压缩被弃路径的要点）与 createBranchedSession（抽出一条干净路径另存）。

3. SessionManager 树 API（对照着记）

API作用
getEntries() / getTree()全部条目（不含 header）/ 整棵树结构
getPath() / getLeafEntry() / getChildren(id)根到当前叶路径 / 当前叶子 / 某条目的孩子
branch(entryId)把 leaf 移到该条目 → 开新分支
branchWithSummary(id, summary)开分支并附上被弃路径的总结条目
createBranchedSession(leafId)把某条路径抽出为新文件
appendLabelChange(id, label)给条目打标签（checkpoint 标记）

构造方式（SDK 层）：SessionManager.create(cwd)（新会话落盘）、inMemory()（测试/无持久化）、open(path)（打开指定 jsonl）、continueRecent(cwd)、list / listAll。前面课程里你看到 SessionManager.inMemory() 一直出现在示例里——它就是「不落盘的会话」，很适合测试与一次性任务。

4. 消息的磁盘形态（你会解析它）

你要做 workflow、要持久化自己的中间产物或解析历史时，需要认得内容块：

内容块字段
texttype + text
imagetype + data(base64) + mimeType
thinkingtype + thinking
toolCalltype + id + name + arguments

助手消息带 api/provider/model/usage/stopReason；toolResult 带 toolCallId/toolName/isError/details。注意 stopReason: "pending" 只存在于流式中间态，落盘前会被替换成终止原因——JSONL 里永远看不到 pending。
