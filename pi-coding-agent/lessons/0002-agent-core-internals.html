Agent 核心内部：状态、事件与钩子

第 1 课给了你旅程全景。这一课钻进最内层——@earendil-works/pi-agent-core 的 Agent 类——看清它到底拿什么做决定，以及你在哪几个点可以插手。

本课成果：理解 Agent 的「状态即真相」，看透 single-flight 与两个队列的源码由来，并知道五个钩子（hook）各自在循环里的位置与用途——这些是你在自己应用里嵌入 pi 时的真正杠杆。

1. 状态即真相：state 里有什么

读 packages/agent/src/types.ts 的 AgentState（源码核实）：

state = {
  systemPrompt: string,        // 每次模型请求都带
  model: Model,                // 未来回合用的模型
  thinkingLevel: ThinkingLevel,// off | minimal | low | medium | high | xhigh | max
  tools: AgentTool[],          // 本 run 可用的工具
  messages: AgentMessage[],    // transcript——上下文
  isStreaming: boolean,        // 只读：是否在跑
  streamingMessage?,           // 只读：当前流式中的部分助手消息
  pendingToolCalls: Set,       // 只读：正在执行的工具调用 id
  errorMessage?,               // 只读：最近一次失败回合的错误
}

三个只读字段是循环运行时的「仪表盘」，五个可变字段是你编程时唯一需要关心的输入。messages 与 tools 的 setter 会复制数组——赋值不会被外部数组的后续修改影响。

核心心智模型：Agent 不做别的——它只是「对着 state 里这堆输入，跑到没活干」。你想改变行为，几乎都是改 state 的五个可变字段（换 model、改 tools、注入 messages、改 systemPrompt）。

2. 单飞约束的源码形态

agent.ts 里有一个 activeRun 槽位：

private activeRun?: ActiveRun;
async prompt(...) {
  if (this.activeRun) throw new Error("Agent is already processing. Use steer() or followUp()…");
  … this.activeRun = { promise, abortController };
}

后果（第 1 课提过，这里看源码）：正在流式时再 prompt() 直接抛错。于是有了两条替代路径：

  • steer(message) → 塞进 steeringQueue：当前回合的 工具调用结束 后注入，适合「插话纠偏」。
  • followUp(message) → 塞进 followUpQueue：agent 本该停止 时再续跑，适合「等你忙完再说」。

队列行为由 QueueMode 决定：one-at-a-time（默认，每次排空只放一条最老的）或 all（一次全放）。

3. 五个钩子：你在循环里的插手点

Agent 构造函数接收一组可选钩子，都在 agent-loop.ts 里被调用（已核实行号语义）：

钩子何时被调典型用途
transformContext每次 streamAssistantResponse 调 LLM 之前（AgentMessage[]→AgentMessage[]）注入/改写发给模型的上下文；压缩就是在这里接入的
prepareNextTurn内层循环每回合之间（收到上一回合 lastCompletedTurn）回合间隙换模型/换 thinking 等级/改上下文——模型切换器就挂这
beforeToolCall工具执行前（已解析并校验参数后）返回 { block: true } 可拦下工具，安全闸门
afterToolCall工具执行后、结果定稿前逐字段覆盖 content/details/isError 等
shouldStopAfterTurn每个 turn 结束后返回 true 提前结束整轮 run

另有 convertToLlm：在 LLM 边界把 AgentMessage[] 转成模型 Message[]。默认只保留 user/assistant/toolResult 三角色——custom 角色消息就此被过滤，不给模型看到。想要自定义角色进上下文？自己给一个 convertToLlm。

4. 事件推进状态：一个 switch 就讲完

agent.ts 的 processEvents() 是所有事件归口的单点：先按事件类型更新内部状态，再把事件广播给订阅者。逐条对（源码核实）：

事件状态副作用
message_start / message_updatestreamingMessage = 该消息（流式中的部分助手消息）
message_endstreamingMessage 清空；消息 push 进 transcript（这是消息落库到 state 的唯一时刻）
tool_execution_start把 toolCallId 加入 pendingToolCalls
tool_execution_end从 pendingToolCalls 移除该 id
turn_end若助手消息带 errorMessage → 写入 errorMessage
agent_endstreamingMessage 清空

注意：消息只有在 message_end 才进入 transcript。订阅者若想在消息定型前拦截/展示流式内容，盯 message_update；想拿到已入 transcript 的完整消息，盯 message_end。

5. run 的收尾：比 agent_end 再多一层

processEvents 里，广播 agent_end 之后并不代表进程结束——还要等所有监听该事件的 listener settle。而在 AgentSession 侧，run 结束后还有 session 的后处理（retry/compaction），最终才发 agent_settled。所以在最内层你要的是 waitForIdle()，在 SDK 层你要的是 agent_settled。
