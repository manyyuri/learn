三种 Mode：同一台引擎的三种驾驶舱

你平时敲 pi 进的是交互式 TUI；pi "任务" 走的是 print；还能 pi --mode rpc 以 JSON 协议对外服务。三者共用同一套核心与 session 逻辑，只是「驾驶员」不同。这一课理清它们的关系，以及 SDK 站在哪里。

本课成果：理解 mode 是「贴在 AgentSessionRuntime 上的壳」，看清 interactive / print / rpc 各适合什么，以及「SDK 直连 vs RPC 子进程」的取舍——这决定你 workflow 应用要不要、怎么暴露 agent 服务。

1. 共同地基：AgentSessionRuntime

三种 mode 都构造在同一个 runtime 上（第 1 课的地图第 ④ 层）。runtime 的意义：它拥有「替换当前会话」的能力（new / resume / fork / import）——因为换会话时要重建与 cwd 绑定的服务，单靠一个 AgentSession 不够。

const runtime = await createAgentSessionRuntime(createRuntime, { cwd, agentDir, sessionManager });
// runtime.session 会在 newSession()/switchSession()/fork() 之后变化
// 换会话后要重新订阅：subscriptions 绑定在 session 上，不在 runtime 上

SDK 文档里那段 createRuntime 工厂（createAgentSessionServices → createAgentSessionFromServices）反复出现，就是为了给三种 mode 提供统一底座。你现在自己写驱动时，大概率也要先搭这个 runtime。

2. 三个驾驶舱

Mode形态典型入口适合
Interactive全功能 TUI：编辑器、历史、全部内置命令InteractiveMode(runtime, opts).run()人机交互；你甚至可以复用其编辑器能力
Print单发：发 prompt、输出结果、退出runPrintMode(runtime, { mode: "text"|"json", initialMessage })脚本化「问一句答一句」；json 模式拿全事件流
RPCJSON-RPC over stdio 的常驻服务runRpcMode(runtime)；或直接 pi --mode rpc --no-session跨语言/子进程集成

3. SDK vs RPC：两种嵌入方式

这是你 workflow 应用迟早要做的抉择（SDK 文档原文表意整理）：

SDK（同进程 import）RPC（子进程 + JSON 协议）
类型安全完全（TS 类型直连）弱（协议文本）
进程隔离无（共享内存/崩溃同生）有（agent 崩了宿主不崩）
语言限 Node/TS任意语言
状态访问直接拿 state/messages经协议消息
每步定制随时换 model/tools/钩子受限
给你的判断准则：你的「固定 workflow」应用是编排者——每个步骤要精细控制工具、上下文、模型 → 用 SDK 直连最顺（这也是你选的路）。若以后你想把 agent 能力暴露给「别的语言写的调度器」，或想隔离崩溃，才切 RPC。

4. 三种 mode 是怎么共享代码的

它们没有各自复制一份 agent 逻辑。共同的管线是：mode → createAgentSessionRuntime → createAgentSessionFromServices（造 AgentSession）→ Agent（跑循环）→ pi-ai（调模型）。mode 层只负责「输入怎么来、输出怎么呈现」：interactive 接键盘与 TUI，print 接参数与 stdout，rpc 接 stdin 的 JSON-RPC 帧与 stdout 响应。想加第四种驾驶舱（比如 webhook 触发、队列消费）？照这个模式写一个就行。
