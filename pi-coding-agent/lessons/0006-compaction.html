压缩 Compaction：上下文窗口不够时的取舍

长会话最大的敌人是上下文窗口。pi 的做法不是「丢历史」，而是「压缩成 checkpoint 总结，保留最近的真实消息」。这一课看清它何时触发、怎么选切点、总结如何生成。

本课成果：理解压缩的三要素——触发条件（阈值）、切点选择（在 turn 边界砍、留最近 N tokens）、总结格式（结构化 checkpoint）。这直接关系你 workflow 里「长任务跑着跑着上下文爆了」怎么办。

1. 三个默认设置（源码核实）

DEFAULT_COMPACTION_SETTINGS = {
  enabled: true,
  reserveTokens: 16384,    // 窗口预留：还剩这么多就触发
  keepRecentTokens: 20000, // 切点之后保留的最近 token 预算
}

触发判断（shouldCompact）：contextTokens > contextWindow − reserveTokens。也就是说模型窗口假设如 200k，当上下文估算超过 200k−16k ≈ 184k 时，下一次后处理就会触发压缩。

2. 上下文用量怎么估

压缩不重新数一遍每条消息，而是：

  • 优先用最后一条有效助手消息的 usage（模型自己报的 totalTokens，来自 provider 的真实统计），加后面几条消息的估算。
  • 没有 usage 可用的消息用估算：chars ÷ 4 的启发式，图片按 ~4800 字符估；实现刻意保守偏高估，宁早压不晚压。

（calculateContextTokens 优先 usage.totalTokens，回退到 input+output+cacheRead+cacheWrite 求和。）

3. 何时触发：三种 reason

session 发出的 compaction_start 带 reason，三种来源：

reason场景
threshold正常路径：某回合结束，上下文超过窗口−预留 → 后处理触发
overflow溢出恢复：上下文真的爆了/接近爆（含被 abort 的响应留下残留）→ 紧急压缩；每次 run 只尝试一次恢复
manual用户/应用主动调 session.compact()

触发时机在 session 层：run 结束后的后处理（_checkCompaction），或下一条 prompt 提交前（catch 上次 abort 的残留）。压缩完若还不够，会再 continue 跑。

4. 切点：尽量别把一句话劈成两半

findCutPoint 的逻辑（源码核实）：

  1. 先找出「合法切点」——通常是 turn 起点的 user 消息位置（compaction 条目本身不算）。
  2. 从最新往回走，累积消息估算 token，直到达到 keepRecentTokens 预算 → 锁定一个「尽量新的合法切点」。
  3. 若切点落在某个 turn 中间（消息太大塞不下预算），会标记 isSplitTurn：把该 turn 的前半段单独压缩，后半段真实保留——这样断掉的回合也能续上。

结果：旧的压缩成总结，最近的 ~20k token 保持原样。模型看到的是一份「checkpoint + 新近原始消息」，不是全部被抽象掉。

5. 总结长什么样

总结由模型按固定的结构化格式生成（SUMMARIZATION_PROMPT，源码里就是一大段指令），要让「另一个 LLM 能接着干」——这是刻意设计：压缩的产物是给未来模型当上下文用的，不是给人看的纪要。分 turn 前缀另有专门格式（Original Request / Early Progress / Context for Suffix）。可用 customInstructions 引导总结侧重（比如「记住待办事项」）。

压缩本身要调用模型，所以也会产生 usage；若总结生成失败，session 有一套 summarization_retry_* 事件做重试。压缩结果作为 compaction 条目写进会话文件——旧消息不删，只是不再进上下文。
